# srbench — a benchmark for SR calibration **methods**

You have a new way to recover SR parameters `(eta, beta, epsilon, kappa)` from a cohort's death
times. This tells you whether it is actually better than what the lab uses now — on five axes at
once, paired against a shipped reference, with every number carrying its denominator and every
regime it was *not* measured on named beside it.

It benchmarks **methods**, not the model. Every cohort here is generated by the SR model itself, so
every result is a self-recovery measurement: how well does a fitter invert a process known to
describe the data exactly. Nothing here says the SR model fits real survival data.

---

## Quickstart

```bash
export SRBENCH_SUT=".../code_5/SRtools_kappa"      # only for building the library
PY=python                                          # Python 3.14

# once, ~20 min: build the cohort library (the arrays are not committed; they are
# deterministic, and the committed manifest's checksums make the rebuild verifiable)
$PY -m srbench.library.build

$PY -m srbench.cli library info        # what you have
$PY -m srbench.cli methods             # what is registered, and is it contract-valid
$PY -m srbench.cli gates               # the 15 gates, each with the failure it was written against
```

Then, for your own method:

```bash
# 1. write an adapter          -> docs/adding-a-method.md
# 2. does the harness accept it?
$PY -m srbench.cli methods
# 3. what will it cost?  (measured, not believed)
$PY -m srbench.cli cost --method mine
# 4. smoke test: 30 cohorts, so a wiring mistake costs 30 calibrations and not 360
$PY -m srbench.cli run --method mine --tier quick
# 5. the real measurement
$PY -m srbench.cli run     --method mine --tier medium
$PY -m srbench.cli score   --run runs/<id>.json
$PY -m srbench.cli compare --run runs/<id>.json --out reports/
$PY -m srbench.cli explorer --run runs/<id>.json --out reports/
$PY -m srbench.cli verify  --report reports/comparison.md
```

Step 5 costs only what step 4 did not already do: quick's 30 calibrations are **reused**, not
recomputed.

## Running it on the cluster

A medium-tier run is ~360 calibrations of roughly 20 CPU-minutes each, so it belongs in an LSF
array, one element per cohort. The store is content-addressed and written atomically, so hundreds
of concurrent elements cannot collide: each writes a different key, and a duplicate write of the
same key is a no-op. That is what makes the array **resumable** — re-submitting recomputes nothing
that already landed.

`cluster/submit.sh` sizes the array and submits it; `cluster/run_task.sh` is the array element.

**The resource sizing is in `submit.sh` on purpose, not in your shell history.** 1 core and 1 GB,
both measured. ⚑ Do not pad the memory: LSF *reserves* what you ask for, on the node, for the job's
whole lifetime — unlike `-W`, where generous is free. Asking 8 GB against this workload's 165 MB
footprint once held ~80 GB idle and drew a complaint from the cluster admin. A few minutes after
dispatch, check it and act on it while a resubmit is still cheap:

```bash
bjobs -l <jobid> | grep -E "MEM Efficiency|MAX MEM"    # under ~30% => kill and resubmit
```

Then bring the results home:

```bash
# on your machine: pull the cluster's store, then merge it into yours
rsync -a wexac:sr_calibration_tester/data/store/ /tmp/cluster-store/
$PY -m srbench.cli merge /tmp/cluster-store --dry-run   # what would arrive
$PY -m srbench.cli merge /tmp/cluster-store
```

**The source store is never modified** — not written, not moved, not unlinked. It holds hundreds of
CPU-hours, and a merge that tidied up after itself would turn one bad run into permanent loss. Pull
and merge as often as you like, including while the array is still finishing; re-merging is a no-op.

Two things the merge does rather than hide:

* **Old-schema results are re-keyed on the way in, not re-run.** If the key schema changed while
  your batch was in flight, its results arrive at addresses that no longer exist. The content is not
  stale, so the merge recomputes the address from components the record already carries. Re-running
  would pay twice for one answer.
* **A conflict is reported, never resolved by preference.** If your store already holds a
  *different* result at the same address, something that changes the answer is missing from the key
  — usually a method whose behaviour changed without its `version` being bumped. The merge names it,
  overwrites nothing, and carries on, so one bad cohort cannot block 359 good ones.

If a key-schema change re-keys your store, the run manifests in `runs/` still point at the old
addresses and will refuse to load. Repoint them — again without recomputing anything:

```bash
$PY -m srbench.cli migrate --manifests runs --dry-run
$PY -m srbench.cli migrate --manifests runs
```

## The four things worth knowing before you use it

**1. Nothing expensive is ever computed twice.** Every calibration is stored, content-addressed on
everything that could change its value. Re-running costs nothing; growing a run computes only the
new cohorts; adding a plot, a statistic, a gate, or a *different reference* costs **zero**
calibrations. `srbench store plan` tells you the reuse/compute split before you commit.

> The one thing you must get right: **bump your method's `version` whenever its behaviour
> changes.** It is part of the store key, so an unchanged version after a real change makes the
> store serve you the old results silently. Everything else in the contract fails loudly; this one
> fails quietly.

**2. A coverage number alone is never a result.** `null_prior` ships with the harness: it ignores
the data entirely and returns its prior box. On the predecessor benchmark an estimator exactly like
it covered the flattest parameter at **1.0000 on all 462 cohorts** — better than the method that was
actually selected. So its figures print beside every coverage you see, and the acceptance rule is
composite: a method supersedes the reference only if it **wins calibration without losing
availability, information or accuracy**. Cost is reported and never decides.

**3. Declining is a result, not a failure.** If your method cannot constrain a parameter, return
`shape: "none"`. It is excluded from the coverage denominator and reported as a decline rate. The
reference declines `kappa` on most cohorts and that is the correct answer. What is *not* free is
declining a lot: availability is one of the five axes, and `decliner` ships to prove the rule
catches it.

**4. The scope is stated, always.** Results are reported **per arm** — `pure`, `hazard`, `window`,
`het`, `censor`, `realfull` — and never pooled across them. A coverage measured on pure-SR cohorts
does not transfer to a cohort with a background hazard, and 24 of 27 real fits have at least one
such feature. Whatever your run did not cover is named next to the verdict.

## What is in the library

**1,990 cohorts** in the tiered body (1,992 planned, 2 excluded — see below), a fixed **ordered** list. Every sizing mode takes a prefix of it, which is what keeps
two methods of different speeds comparable: the shorter prefix is a subset of the longer, so the
paired comparison survives on the shorter one.

| tier | cohorts | what it supports |
|---|---:|---|
| quick | 30 | a smoke test. Pooled verdict only — **no per-arm and no per-stratum claim** |
| medium | 360 | a pooled verdict per arm |
| full | 1,990 | per-stratum claims and the paired comparison across removal half-saturation |

Plus one **optional block, outside every tier**, selected whole by name rather than as a prefix:

| group | cohorts | what it supports |
|---|---:|---|
| `nladder` | 300 | the n-dependence view: n = 150, 500, 1000, 3000, 10000, with **every** parameter point at **every** rung |

```bash
$PY -m srbench.cli run --method mine --group nladder     # ~49 CPU-hours; not part of any tier
```

Adding it is why the library is at **v2**. An optional block is *appended*, never interleaved, so
every tier is still a prefix of the same 1,990 cohorts and means exactly what it did before — and
because `library_version` is not in the store key, growing the library invalidated **nothing**:
1,990 observation digests compared, 0 different, `--tier full` still reports `to compute 0`.

Seven values of `kappa` — five across `[0.01, 1]`, where all 27 real fits live, plus 2 and 10 as
probes — with 24 manifold points each, chosen by **measuring** what each value can reach rather than
by gridding. See `specs/001-sr-method-benchmark/library-design.md`.

All 27 real fitted cohorts are in, twice: in `pure` at their own fitted parameters, and in
`realfull` with the observation model each actually had. The difference between the two **is** the
cost of the real observation model, per cohort.

**Two cohorts were excluded at build time** — the same parameter point at δ/L = 0.1 has only two
distinct death times, so it cannot carry a window and does not belong in the arm that measures
windowing. The manifest records which and why, which is why the built library is 1,990 rather than
the planned 1,992. `srbench library info` prints this, along with the 12 real fit windows that
contain all of their cohort's deaths (non-binding, and that is the real observation model).

## Layout

```
srbench/contract/   the published interface (types, one validator, the registry)
srbench/library/    feasibility, point selection, build, frozen load, the window transform
srbench/store/      content-addressed, immutable, concurrent-safe result store
                    (+ merge: cluster -> local, and migrate: re-key on a schema change)
srbench/score/      floors, combinations, claims, pairing, the five axes and the verdict;
                    ridge: how tightly a fit's own near-optimal points pin a combination
srbench/gates/      15 gates, each with its motivating failure and a fixture it fails on
srbench/run/        sizing modes, cost probe, execution
srbench/report/     the comparison, and an INDEPENDENT verifier
srbench/explorer/   the standalone explorer: payload, view registry, assembler
methods/            shipped adapters: mle_profile_jax2 1.0.1 (the reference since 2026-10-27, library v6;
                    1.0.0 on library v5 was the reference 2026-10-13 to 2026-10-27; the package also
                    registers mle_profile_jax2_h and six kfix names, none of them the reference),
                    mle_profile_jax (v0.3.3, the reference 2026-09-26 to 2026-10-13),
                    mle_profile (the reference before that), null_prior, decliner, fast_stub
```

**Only the library builder and the three estimator adapters import the system under test**:
`library/build.py`, the `mle_profile` adapter, `mle_profile_jax` and `mle_profile_jax2` (read-only: its seed, grid rule,
Kaplan-Meier and `profile_ci`). Everything else — all scoring, all gates, the whole default test suite — runs on frozen
data and stored results.

## Tests

```bash
$PY -m pytest -q        # ~250 tests, seconds, ZERO production calibrations
```

Anything that performs a real calibration is marked `slow` and excluded by default. A fixture
asserts that no default-suite test imports the system under test, so the standalone property is
enforced rather than hoped for.

The explorer is tested by **actually rendering it** in headless Chrome and failing on any page
console message — a view whose JavaScript throws leaves an empty panel, which looks exactly like a
method with no results. Those tests skip where Chrome is absent, so the suite still runs on a
cluster node. The console detector is itself tested against a deliberately broken page: a green
test that cannot fail would be worse than no test.

## The rules this repository is built on

`.specify/memory/constitution.md`. Briefly: measure, never assert · no hardcoded numbers in any
artifact · every comparison states its denominator and whether it is paired · a non-claim is not a
hit · a gate earns its place by catching something real.
